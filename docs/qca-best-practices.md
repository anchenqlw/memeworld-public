# 把 QCA 当作长期运行时：Me&Me 的七条实践

> 最后更新：2026-07-15

Me&Me 最重要的技术判断是：QCA 不只是“帮我完成一次任务”的 Agent，也可以成为产品运行时的一部分。

一只小猫需要在用户离线时继续旅行，需要记得过去发生过什么，需要在下一次对话里保持身份连续，还要能被暂停、修复、轮换凭据和审计。这些要求迫使我们从“写一个好 prompt”转向“设计一个长期系统”。

## 1. Agent 属于用户，而不是平台的影子账号

小猫的 QCA Identity、Template、Schedule、Session 与 Memory 位于用户自己的 QCA 账号边界内。Me&Me 只代用户创建、更新或归档带有明确应用标记的资源，不碰与产品无关的 Agent。

这样做有三个价值：

- 资源归属和 Credits 关系清晰；
- 用户能够在 QCA 一侧看到长期运行的 Agent；
- 平台无法因为“方便”而自然扩张到用户账号的其他资源。

## 2. 一只长期 Agent 是资源组合，不是一段 prompt

在 Me&Me 中，一只猫至少包含：

| 资源 | 作用 |
|------|------|
| Identity | 稳定身份与外部幂等标识 |
| Template / Config | 版本化的人格、工具和行为约束 |
| Schedule | 离线时的定时触发 |
| Session | 保持一次次旅行或对话的连续性 |
| Memory | 长期成长、偏好与经历 |
| Allowlist | 限制可访问网络与产品接口 |

拆开这些资源后，身份可以稳定，行为可以升级，Schedule 可以暂停，Memory 可以保留，故障也可以逐项修复。

## 3. 任务先进入仓库，再进入 QCA

长期任务不应该只存在于控制台的一句 prompt 中。Me&Me 先把任务固化为版本化定义，再由服务端渲染成 QCA 可执行内容。

这意味着：

- 任务为什么变化可以审阅；
- 一次线上行为能够追溯到具体版本；
- 控制台与仓库漂移可以被对账；
- 回滚时有明确的上一个定义。

任务文件描述“做什么”，运行控制面决定“现在是否允许做”。`enabled: true` 不是完整授权。

## 4. Memory 应该可见、可纠正、可分层

长期记忆会直接塑造 Agent，因此不能把它当作不可见的模型副作用。

Me&Me 把记忆区分为：

- 主人主动提交的成长卡片；
- 小猫从旅行和互动中形成的日记；
- 用于保持人格连续的稳定档案；
- 仅供当前任务使用的短期上下文。

用户可以看到并纠正自己主动提交的内容。面向未来社交的摘要默认不公开，只有用户明确授权后才允许交换。

## 5. 调度必须确定，生成可以灵活

语言模型擅长生成旅行故事、观察与回应，但不适合决定分布式调度真相。

这些能力应由确定性系统负责：

- cursor 与分页；
- idempotency key；
- lease、heartbeat 与超时；
- retry、dead-letter 与预算；
- 依赖 DAG 与并发上限；
- 环境、身份与权限校验；
- circuit breaker。

一个简单判断：如果重复执行会制造第二个 PR、第二次旅行或第二份奖励，就不能只靠 prompt 里的“请勿重复”。

## 6. 最小权限是产品能力

权限边界不只属于安全文档，它会直接影响用户是否敢把 Agent 长期托管在云端。

Me&Me 将权限分成不同层：

- 用户 PAT 只在服务端加密托管，不进入浏览器、日志或仓库；
- QCA 资源操作限制为带应用标记的白名单类型；
- 小猫访问产品 API 使用独立、可轮换、只存哈希的凭据；
- Agent 的工具和出网域名按任务最小化；
- 开发、复核、发布与监控身份互相分离。

## 7. 过程需要可回放，人保留最后决定

多 Agent 协作最危险的失败不是某一步报错，而是“看起来完成了，却没有人说得清发生了什么”。

Me&Me 使用一条统一关联链：

```text
feedback → cluster → work item → job/run → branch/PR → head SHA
→ staging deployment → production bundle → observation → verified
```

复核绑定 exact head SHA；代码变化后旧复核失效。合并批准与生产发布是两个不同的人类闸门，不能互相推定。

## 最后的原则：Agent 必须学会停下

当核心指标恶化、证据链断裂、权限漂移或安全审计异常时，系统首先冻结变更，而不是继续重试。

一个能停止的 Agent 系统，才有资格长期运行。
